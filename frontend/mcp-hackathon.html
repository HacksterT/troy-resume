VA OIG Recommendations MCP Server

An MCP server that lets an AI assistant answer questions across VA Office of Inspector General reports: which findings recur across facilities, whether a theme is growing, what peer facilities did to fix a problem, and how long similar recommendations take to close. Every answer traces back to a report number and a link.

The problem

VA OIG publishes every report and recommendation it issues, and its website is good at finding individual documents. It cannot answer questions that span documents. Today those answers take hours of reading PDFs, so much of the cross-facility learning they could support does not happen.

VA acts on most of what it is told. The gap this project addresses is not whether VA closes recommendations. It is whether one facility can learn from the findings issued to the others.

vaoig.gov offers full-text search and filters by report type, topic, office, state, VISN, status, and age. Those tools return lists of documents; the person searching still has to open each report, compare it with others, and count. There is no API or bulk export, and the most actionable content, each facility's response with its target date and corrective action, appears only in the report PDFs.

Who it serves

Facility patient safety and quality staff

Anticipate what an OIG inspection will examine, check whether the facility shares weaknesses peers were cited for, and show leadership that recurring national findings were addressed locally.

VISN and VHA program offices

Spot systemic findings that call for a national fix rather than facility-by-facility correction.

Oversight and accountability staff

Track the age of open recommendations and closure performance by office and topic.

Veterans, VSOs, congressional staff, journalists

Ask in plain language what OIG found at a facility and what was done about it.

What the server makes possible

Preparing for an inspection

OIG's Healthcare Facility Inspection program reviews each VHA medical facility on an approximately three-year cycle across five domains: culture, environment of care, patient safety, primary care, and the Veteran-centered safety net. A patient safety manager whose facility is coming due asks what peers were cited for, which findings recur, and what those facilities did in response. The server provides the facility's own prior findings and whether they closed, recurring peer findings and how common each one is, each peer's committed corrective action and target date, and links to every source report.

The current data holds 283 groups of recurring findings. The largest in current inspections, on developing workflows for communicating test results, appears in 21 of the 112 Healthcare Facility Inspection reports.

Seeing whether a theme is growing

A VISN patient safety officer asks whether suicide-risk and safety-plan findings are rising. On the website, that means repeating a search for each year and tallying the results. The server returns it year by year with open counts and typical time to closure.

Reports with such recommendations, from an earlier analysis through 2024: 7 in 2015, 35 in 2016, 23 in 2020, 35 in 2021, 31 in 2023, 51 in 2024.

Reading a pattern honestly

Reports with recommendations that mention test or laboratory results numbered 32 and 27 in 2015 and 2016, then 2 to 11 a year through 2024, then 21 and 28 in 2025 and 2026 so far. It is tempting to say facilities improved and then slipped. The data cannot support that alone: OIG inspects against a protocol, so the rise could reflect the topic returning to that protocol as much as any change in care, and the same goes for the earlier drop. On October 19, 2026, OIG issued an inspection report for the VA Phoenix Health Care System recommending written workflows for communicating test results under VHA Directive 1088. The server presents both readings with the counts rather than choosing one.

Tracking closure performance

OIG publishes a closure date for each recommendation. The server turns those dates into time-to-closure figures and not-implemented rates by office, topic, and report type, compared against what OIG publishes. A closure date appears to record when OIG closed a recommendation after reviewing evidence, so these figures describe OIG's process as well as the facility's. The server does not report whether facilities met their target dates.

Explaining a facility to the public

A Veteran or advocate asks what OIG has found at their medical center. The server returns every report and recommendation for that facility in plain language, with status, closure date, and the published facility response.

Approach

Two parts: a data service that turns OIG's public pages and PDFs into a structured, queryable dataset, and an MCP server that gives AI assistants goal-level tools over that dataset.

Data

A polite, identified crawler that follows robots.txt collects OIG's report listings, report pages, and report PDFs. It captures OIG's own classifications (report type, topic, Major Management Challenge, action office, state, VISN), each recommendation's text, status, action office, and closure date, and, from inspection reports, the domain, concurrence, target completion date, corrective action, and standards cited for each recommendation. The data lives in a structured database behind a documented JSON API, with one search that blends keyword and semantic matching. Each build is compared with what OIG publishes, and a build that fails those checks is not published.

MCP tools

ToolWhat it answers
Search findingsRecommendations and corrective actions matching a question in any wording, filtered by topic, office, status, report type, VISN, state, or date
Analyze recommendationsExact counts and measures grouped by year, office, topic, or report type: trends, open counts, time to closure, and aging
Systemic clustersRecurring recommendations across reports, with how common each one is and how long similar findings take to close
Facility profileEverything OIG has reported about one facility, with responses, closure dates, repeat findings, and an estimated next inspection window
Report detailOne report with every recommendation, status, closure date, response, and standards cited
Inspection briefOne facility's preparation in one request: its history and open findings, the most common peer findings, what peers committed to do, and an estimated next window
Dataset statusWhat the data covers, when it was collected, and how it compares with OIG's published totals

The tool list is deliberately short: new facts become fields on these tools rather than new tools. The server also publishes reference lists of topics, offices, and facilities, and guided prompts for clients that support them.

Safeguards

  • The server returns structured records; the assistant summarizes them. It does not generate findings.
  • Every claim carries a report number and link, and every response states when its data was collected.
  • Where data supports more than one interpretation, the server says so.
  • The server describes what OIG found and what facilities reported. It does not rate facilities or individuals.

Evaluation

Planned next, with results to follow. An AI assistant with no other context answers realistic multi-step questions using only the server's tools, scored against gold answers computed from a frozen copy of the data: exact matches on counts and report numbers, precision and recall on lists, tool selection, caveats, and a citation-integrity check that every cited report exists. Traces are logged with Arize Phoenix. PDF extraction is checked separately against a hand-labeled sample.

Limits

The server is not a replacement for VA's internal tracking of OIG recommendations, which is organized around compliance with each recommendation; it is built for learning across facilities. Recurrence of a finding does not by itself show that facilities fail to learn from one another, because OIG inspects against a standard protocol and will find what it looks for. Statuses change after each refresh, so every answer carries its data date.
