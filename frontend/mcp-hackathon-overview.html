MCP Overview

VA OIG Recommendations Assistant

The VA Office of Inspector General (OIG) has published about 4,410 reports. Its website is good at finding a document. It is not built to answer a question that spans many documents, such as "what keeps being cited?" or "what did other facilities commit to do about it?" Today, answering those questions means hours of reading reports and PDFs.

In brief

This project connects an AI assistant to a structured copy of what OIG publishes, currently 4,410 reports, 15,649 recommendations, and 11,264 facility responses drawn from report PDFs. Staff ask a question in plain language and get an answer drawn from across all of them, with a report number and link for every finding. The connector is called an MCP server, which is simply a standard way for an AI assistant to use an outside data source. It runs in IBM's watsonx Orchestrate, where an AI assistant uses it.

It uses only public information from vaoig.gov and no internal VA systems. It is not an official VA or OIG product, and it does not replace VA's own tracking of recommendations.

Where it goes beyond OIG's website

OIG's search is solid, and this project does not try to replace it. If you know what you are looking for, the site's keywords and filters will find it, and every answer here links back to the site. The difference is in what happens after the search.

The tools

The server exposes a short, deliberately small set of goal-level tools. New facts become fields on these tools rather than new tools, and it also publishes reference lists of topics, offices, and facilities, and guided prompts, with suggested values, for clients that support them.

ToolWhat it answers
Search findingsRecommendations and corrective actions matching a question in any wording, filtered by topic, office, status, report type, VISN, state, or date
Analyze recommendationsExact counts and measures grouped by year, office, topic, or report type: trends, open counts, time to closure, and aging
Systemic clustersRecurring recommendations across reports, with how common each one is and how long similar findings take to close
Facility profileOne facility's reports, inspections, and recommendations, with status, closure dates, repeat findings, and an estimated next inspection window
Report detailOne report with every recommendation, status, closure date, response, and standards cited
Inspection briefOne facility's preparation in one request: its history and open findings, the most common peer findings, what peers committed to do, and an estimated next window
Dataset statusWhat the data covers, when it was collected, and how it compares with OIG's published totals

Safeguards

  • The server returns structured records; the assistant summarizes them. It does not generate findings.
  • Every finding the server returns carries a report number and link, and every response states when its data was collected.
  • Where data supports more than one interpretation, the server says so. A facility name that could mean several facilities returns every match, and in clients that support it a question to the user, never a guess. Shown in Claude Code, the question halved the round trips against asking in chat and cut tokens 39 percent (five runs each way, one question).
  • The server describes what OIG found and what facilities reported. It does not rate facilities or individuals.
  • During the hackathon, including judging, each question the server receives and the answer it returns are recorded, so the builder can see how it is used. Nothing nonpublic belongs in a question.
  • Text from OIG reports reaches the assistant marked as quoted source material, not instructions, and every tool only reads, so nothing written in a report can make the server act.

Security

The data is public, so security here means keeping the service from being misused, keeping its credentials private, and keeping a model from being steered by what it reads. The design, every check with its latest result, and an independent review are in SECURITY.md.

  • Locked at both ends. The hosted server answers only callers with a bearer token, and reaches the data service through Cloudflare with a second token and the service's own key. In watsonx Orchestrate it runs inside Orchestrate's runtime, with no network address of its own.
  • Narrow by design. Seven read-only tools. No tool writes, runs commands, or reaches any address but the data service. Every input is typed and bounded, so an unexpected value is refused rather than passed on, and each caller is rate limited.
  • Nothing internal leaks. A failure returns a short message and a hint, never a stack trace, address, or credential. No credential is committed: a scan of the repository's full history found none.
  • Hard to steer. Six adversarial questions, including an instruction hidden in pasted text and a request to name employees, test the model's side. With the server, Claude Opus 5.5 and Sonnet 5.5 passed 6 of 6, GPT-OSS 120B 4 of 6 in both runs, and Llama 3.3 70B 4 of 6.
  • Checked, not only designed. On November 17 the server passed 15 of 15 image checks, 22 of 22 deployment checks, and 49 of 49 robustness checks that send hostile and malformed input to every tool. Dependencies are audited for known vulnerabilities on every change, with none found. A separate review agent found no high-severity issues; its findings are fixed or recorded as accepted risks.
  • Known limits. Tokens are static and do not expire; a production deployment should use short-lived OAuth tokens. Rate limits live in one process. In Orchestrate every user reaches the data service under one shared identity, and Orchestrate's own access controls decide who can use the agent.

Evaluation

An AI assistant with no other context answers realistic questions using only the server's tools, scored against gold answers computed from a frozen copy of the data: exact matches on counts and report numbers, lists, tool selection, caveats, and a check that every cited report exists. Traces are logged with Arize Phoenix. On the final server, Claude Opus 5.5 passed 23 of 24, against 3 with no server, and Claude Sonnet 5.5 passed 22; both cited every report where required. Neither model cited a report that does not exist. The test is small, and its authors wrote the questions and tuned the server after earlier runs. An independent agent's answers, with notes on how they checked out, are in the test bank.

The same server and questions ran with five models from four model makers. GPT-OSS 120B in IBM watsonx Orchestrate passed 10, 8, and 11 of 24 in a first round and 12 and 12 in a second, with only the server changed; Llama 3.3 70B on watsonx.ai passed 9; DeepSeek V4 Pro, scored a different way, agreed with the gold answers on 18 of 18. Choosing the right tool was not the hard part. The weaker models skipped the citation and data date that every result carries, and many of the server's fixes came from their failures. A server that only meets the best model has not been tested. In one load test on one Mac, not run to failure, all 2,059 calls from 1 to 40 concurrent clients were answered. The method, every result, and its limits are in the evaluation.
